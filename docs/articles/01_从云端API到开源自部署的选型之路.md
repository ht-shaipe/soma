# 数字人口播视频生成：从云端 API 到开源自部署的选型之路

> 用 Rust 写一个 AI 短视频自动生成工具，需要"照片 + 文案 → 口播视频"能力。云端 API 贵，开源自部署又踩了一堆坑。本文记录方案选型全过程。

## 写作前沿

今天发现原来头条号这么干净，就把最近我做数字人口播的过程整理一下，以从这里开始记录。

## TL;DR

- **主力选 EchoMimicV3-Flash**（Apache 2.0、12G 显存、单张 4090 可跑），AutoDL 按量租用，月成本 ¥30-60（100 条）
- **二期选 HeyGem/Duix.Avatar**（HTTP API、支持并发和长视频），需独立 GPU 常驻，月成本 ¥2000-4000
- 对比 HeyGen 云端 API，开源自部署单条便宜一个量级
- 长视频分段拼接后，补齐前音画偏差最大 ~0.7s，tpad 补齐后 <0.1s（详见第 5 篇）

## 需求很简单，选型很痛苦

需求一句话能说清：**给一张人物照片 + 一段文案，生成人物开口说话的口播视频，口型与配音同步。**

但当你真正开始选方案时，会面对一地鸡毛：

- 云端 API（HeyGen）效果好但按条计费，量大烧钱
- 开源模型一大堆，每个都说自己最好
- 2023 年的老模型画质差，2026 年的新模型要 80G 显存
- Mac 跑不动任何 GPU 方案，必须租服务器
- 有的要 Docker，有的要 conda，有的要特定 CUDA 版本
- 协议有的 Apache 2.0 能商用，有的"仅限研究"

我在这个选型上花了整整一天，最终选了 **EchoMimicV3-Flash**，后来又加了 **HeyGem/Duix.Avatar** 作为 HTTP API 方案。本文把选型过程完整记录下来，给同样在做数字人选型的朋友一个参考。

## 一、先盘点自己手里有什么

在选开源方案之前，先看看代码侧已经具备什么：

```
soma-server（Rust）
  ├── digital_human.rs     # 三阶段流水线：TTS音频 → 口播视频 → 字幕BGM合成
  ├── DigitalHumanProvider trait  # submit/poll/download 抽象
  ├── heygen.rs            # HeyGen 云端适配器（已可用）
  ├── sadtalker.rs         # SadTalker 本地适配器（环境未就绪）
  └── soma-tts             # 多引擎 TTS（Edge/SiliconFlow/MiMo/ElevenLabs/Azure）
```

关键发现：**架构已经有了，缺的不是骨架是"引擎"**。`DigitalHumanProvider` trait 定义了 `create_task` / `query_task` / `download_video` 三个方法，换引擎只需要新增一个实现，调用方零改动。

这降低了选型的心理负担——选错了换一个也不贵。

## 二、候选方案横评

### 2.1 第一梯队：2025-2026 新一代音频驱动模型

数据来自 [Tight Studio 2026-08 横评](https://tight.studio/blog/open-source-talking-avatar-models/)，统一素材实测：

| 模型 | 协议 | 峰值显存 | 3.8s 片段耗时 | 短评 |
|---|---|---|---|---|
| **EchoMimicV3-Flash**（蚂蚁） | Apache 2.0 | 12G（官方） | 252s（L40S） | 1.3B 轻量、8 步生成、免 face mask |
| **LiveAvatar**（阿里夸克） | Apache 2.0 | 61.4G | 181s（H200） | 锐度/口型最好，流式实时，但需要 80G 卡 |
| **LongCat-Video-Avatar 1.5**（美团） | MIT | 46.8G | 233s（H200） | 表现力最强，头/半身/手势都会动 |
| **SoulX-FlashTalk**（Soul） | 待确认 | 57.8G | 332s 冷启动 | 分块流式，适合长视频 |
| **Wan2.2-S2V-14B**（阿里） | Apache 2.0 | 58.7G | 780s（最慢） | 电影感强但太慢 |

### 2.2 上一代方案

| 方案 | 显存 | 评价 |
|---|---|---|
| SadTalker（现有） | ~4-6G | 2023 年模型，256p 画质、头部几乎不动 |
| MuseTalk 1.5（腾讯音乐） | ~8G | 实时口型同步，但输入是**视频**不是照片 |
| HunyuanVideo-Avatar（腾讯） | 24G+ | 已被新一代全面超越 |

### 2.3 另一条路：HeyGem/Duix.Avatar

HeyGem 是一个 **Docker 部署的 HTTP API 方案**，三个容器：

```
fun-asr（语音识别） + fish-speech-ziming（TTS 声音克隆） + duix.avatar（视频合成）
```

- 端口 18180 做 TTS，端口 8383 做视频合成
- 支持并发，原生长视频（无 6 秒限制）
- 音画同步精确（由音频驱动口型）
- 但需要独立 GPU 服务器 + Docker 权限

## 三、选型决策

### 主力引擎：EchoMimicV3-Flash

理由：

1. **协议宽松**：Apache 2.0，可商用
2. **显存友好**：官方标称 12G，单张 RTX 4090（24G）富余
3. **推理快**：1.3B 参数、8 步生成，4090 上 10 秒成片约 3-6 分钟
4. **免 face mask**：不需要额外的人脸遮罩预处理
5. **蚂蚁持续维护**：AAAI 2026 论文，ModelScope/HF 镜像可下载

### 为什么不选 LiveAvatar / LongCat？

它们确实更好——LiveAvatar 锐度第一、LongCat 表现力第一。但都需要 **48G+ 显存**（A100/H100/H200 或 2×4090），成本翻几倍。等业务量撑得起再上。

### 为什么不选 HeyGen 云端 API？

- 按条计费约 $0.3-1/分钟视频
- 量大烧钱：1000 条 30s 视频 ≈ $150-500
- 开源自部署单条成本 ≈ ¥0.15-0.3（电费），便宜一个量级

### HeyGem 作为二期方案

EchoMimicV3 有个硬伤：**单次最多 150 帧（6 秒）**，长视频必须分段生成再拼接，补齐前音画偏差最大 ~0.7s，tpad 补齐后 <0.1s（详见第 5 篇）。HeyGem 没有这个限制，但需要常驻服务器（月成本更高）。两者互补：

- **低频/按需**：EchoMimicV3 + AutoDL 按量租用，用完关机
- **高频/商业**：HeyGem + 独立 GPU 服务器常驻

## 四、成本对比

| 维度 | EchoMimicV3 | HeyGem | HeyGen 云端 |
|------|-------------|--------|-------------|
| 服务器 | AutoDL 按量即可 | 独立 GPU 常驻 | 无需服务器 |
| 月成本（100条） | ~¥30-60 | ~¥2000-4000 | ~$30-100 |
| 并发 | 串行 | 支持并发 | 支持并发 |
| 长视频 | 需分段 | 原生支持 | 原生支持 |
| 音画同步 | 补齐后 <0.1s | 精确 | 精确 |

**结论**：生成量不大时 EchoMimicV3 按需最省钱；需要高频生成或商业用途时 HeyGem 更合适。

## 五、最终架构

```
┌─ Mac（soma server）──────────────────┐      ┌─ GPU 服务器──────────────────┐
│ 数字人三阶段流水线                     │      │  EchoMimicV3-Flash 推理      │
│  阶段1 TTS（Edge/CosyVoice 声音克隆） │      │  SSH 远程调用                │
│  阶段2 口播视频 ─────────────────────┼─SSH──▶  echomimic_v3_runner.py     │
│  阶段3 FFmpeg 字幕/BGM 合成           │      │  模型常驻显存               │
└───────────────────────────────────────┘      └──────────────────────────────┘
```

TTS 和字幕合成完全复用已有能力，只换了阶段 2 的引擎。这就是 Provider trait 抽象的价值——**换引擎，调用方零改动**。
