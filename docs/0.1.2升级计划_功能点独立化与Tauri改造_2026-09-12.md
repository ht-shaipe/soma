# 0.1.2 升级计划：功能点独立化 + Tauri v2 桌面应用改造

> 创建日期：2026-09-12 ｜ 分支：`0.1.2`（基线：`0.1.1`）
> 两大目标：
> 1. **功能点独立化** —— 把流水线中每一个步骤（脚本、分镜、TTS、字幕、素材、AI 视频生成、视频合成、数字人…）拆分为可单独调用的独立功能点
> 2. **Tauri v2 桌面应用** —— 从「后端服务 + Web 页面」改造为跨平台桌面 App（复用现有 Rust core 与 Vue3 前端）

---

## 一、现状分析

### 1.1 架构现状

```
web/ (Vue3 + Vite)  ──HTTP──▶  soma-server (Actix-Web 4)
                                   │ handler → service → pipeline
                                   ▼
                     soma-core / soma-tts / soma-stock / soma-video
```

### 1.2 各步骤独立化程度盘点

| 流水线步骤 | 独立 API | 独立 UI 入口 | 耦合点 | 结论 |
|-----------|---------|-------------|--------|------|
| 需求理解 (intent) | ✅ `intent.generate` | ❌ 仅向导内 | 依赖 TaskInfo 上下文 | 半独立 |
| 脚本生成 (scripts) | ✅ `scripts.generate` | ❌ 仅向导内 | 同上 | 半独立 |
| 关键词提取 (terms) | ✅ `terms.*` | ❌ | 同上 | 半独立 |
| 分镜脚本 (storyboard) | ✅ `storyboard.generate` | ❌ | 同上 | 半独立 |
| TTS 配音 | ⚠️ 仅 `voices/preview` 试听 | ⚠️ 仅试听 | 完整合成被锁在 pipeline 第 5 步 | 需拆出 |
| 字幕生成 | ❌ 无独立入口 | ❌ | 与 TTS 绑定在第 5 步 | 需拆出 |
| 素材采集 | ⚠️ `videos.fetchmaterials` 绑定任务 | ❌ | 搜索/下载能力未独立暴露 | 需拆出 |
| AI 视频生成 | ❌ 无独立入口 | ❌（仅日志展示） | 锁在 pipeline 第 4 步 | 需拆出 |
| 视频合成 | ❌ 无独立入口 | ❌ | 锁在 pipeline 第 6 步 | 需拆出 |
| 数字人口播 | ✅ `digital_human.*` 独立任务线 | ✅ 独立页面 | 已是独立任务体系 | 纳入统一注册即可 |
| 声音克隆 | ✅ `/voices/clone` | ✅ 独立面板 | 已独立 | 同上 |

### 1.3 有利条件

- **service 层已与 HTTP 层解耦**（handler → service），业务逻辑不依赖 Actix-Web，可被 Tauri command 直接复用
- **SQLite 持久化 + `stop_at` 断点续跑**已存在：任务产物（脚本/音频/字幕/素材/分段视频）按任务落盘，天然支持「单步产物」的存取
- **前端 Vue3 + Vite** 可直接作为 Tauri 前端（Tauri v2 不限定前端框架）
- **数字人已是独立任务线**，可作为「功能点化」的参考模板
- **preflight_check 环境预检机制**已存在，可复用于桌面版外部依赖探测

### 1.4 主要障碍

- pipeline 各步骤通过 `TaskInfo` 结构体字段隐式传递数据，步骤不可脱离任务上下文运行
- 前端 API 层（`web/src/api/*`）硬编码 HTTP 调用
- 配置/存储路径写死为项目相对路径（`conf/`、`./storage`），桌面 App 需迁移到系统目录
- 外部依赖：FFmpeg（必需）、Python + GPU（数字人引擎），桌面打包需明确策略
- 私有 kit 路径依赖（`../../kit/` 下的 tube / ai-llm-kit），构建机必须存在该目录

## 二、目标架构（0.1.2 形态）

```
┌─────────────────────────────────────────────────────┐
│ Tauri v2 桌面 App（crates/soma-app）                 │
│ ┌─────────────────────────────────────────────────┐ │
│ │ Vue3 前端（复用 web/，API 层加 Transport 抽象）    │ │
│ │   HttpTransport（服务器模式）│ TauriTransport      │ │
│ └────────────────────┬────────────────────────────┘ │
│                      │ invoke() / event 推送         │
│ ┌────────────────────▼────────────────────────────┐ │
│ │ Tauri Commands 层（薄封装，1:1 映射功能点）        │ │
│ ├─────────────────────────────────────────────────┤ │
│ │ Feature Registry（统一功能点注册表）               │ │
│ │  feature.run(input) → FeatureOutput + 进度事件    │ │
│ ├───────┬───────┬───────┬───────┬───────┬─────────┤ │
│ │ 脚本   │ TTS   │ 字幕  │ 素材   │ 视频合成│ 数字人   │ │
│ │ 分镜   │ 声音克隆│ AI视频│ …每个功能点可独立运行     │ │
│ ├───────┴───────┴───────┴───────┴───────┴─────────┤ │
│ │ Pipeline = Feature 编排器（默认链 + 可自由组合）    │ │
│ ├─────────────────────────────────────────────────┤ │
│ │ soma-core / soma-tts / soma-stock / soma-video   │ │
│ └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
  （soma-server 保留：headless 服务器部署模式，共用 Feature 层）
```

**核心原则**：
1. 每个功能点 = `id + 输入 Schema + 输出 Schema + run()`，可脱离任务单独调用，产物落 `storage/features/{feature}/{uuid}/`
2. Pipeline 退化为「功能点的默认编排」，用户可跳过/替换/重排任意步骤
3. 一套 Feature 层，两个宿主：Tauri 桌面（command + event）与 Actix-Web 服务器（HTTP），业务代码零复制

## 三、里程碑拆解

### M1：功能点独立化（纯 Rust 后端改造，不动前端）

| # | 任务 | 内容 | 验收标准 |
|---|------|------|----------|
| M1.1 | Feature 抽象 | 在 soma-core（或新建 `soma-feature`）定义 `trait Feature`：`id()/name()/input/output/run(progress)`，统一 `FeatureInput/FeatureOutput` 信封结构与进度回调 `ProgressReporter` | trait 定义 + 单测通过 |
| M1.2 | 步骤 Feature 化 | 把 pipeline 6 步（intent/script/storyboard/materials/audio+subtitle/compose）改造为独立 Feature 实现，数据传递从「TaskInfo 字段」改为「显式输入/输出结构」；pipeline 改为编排器（保留 stop_at/断点续跑语义） | 原 6 步流水线行为不回归（现有任务跑通） |
| M1.3 | 补齐独立功能点 | 新增独立入口：① TTS 完整合成（文本→音频文件）② 字幕生成（音频→SRT，含 Whisper）③ 素材搜索/下载（关键词→素材列表/文件）④ AI 视频生成（文/图生视频）⑤ 视频后期（拼接/字幕/混音/水印，任意素材输入）⑥ 数字人、声音克隆纳入同一注册表 | 每个功能点可通过 API 单独调用并产出文件 |
| M1.4 | 无任务上下文调用 | 功能点支持「裸调用」：显式入参，产物落 `storage/features/{feature}/{uuid}/`，历史可查 | curl 单步调用成功且产物可下载 |
| M1.5 | 统一 API | 新增 `features/list`、`features/run`、`features/history` 分发端点；旧 API 全部保留兼容 | 新旧 API 并存，前端不改动也能正常工作 |

### M2：Tauri v2 骨架

| # | 任务 | 内容 | 验收标准 |
|---|------|------|----------|
| M2.1 | soma-app crate | 新建 `crates/soma-app`（Tauri v2），加入 workspace；`cargo tauri dev` 能起出窗口 | 空窗口 + Hello 页面运行 |
| M2.2 | 前端 Transport 抽象 | `web/src/api/` 增加 transport 层：`HttpTransport`（现行为）/ `TauriTransport`（invoke），Vite 按环境切换；开发模式仍可走 HTTP 联调后端 | 同一前端代码在浏览器（HTTP）与 Tauri 窗口（invoke）下均可用 |
| M2.3 | Commands + 事件 | 每个 Feature/任务操作映射 `#[tauri::command]`；任务进度由轮询改为 Tauri event 推送（`progress://{task_id}`） | 桌面 App 内创建视频任务，进度条实时推进 |
| M2.4 | 配置与存储迁移 | 配置迁移到 `app_config_dir`，存储迁移到 `app_data_dir`；首次启动执行迁移/初始化向导；`conf/config.toml` 仅服务器模式使用 | 桌面 App 在全新机器上首次启动可用 |
| M2.5 | 外部依赖探测 | 启动时探测 FFmpeg / Python / GPU，缺失时引导安装（复用 preflight_check）；FFmpeg 先要求系统安装，M3 再考虑 sidecar 捆绑 | 缺 FFmpeg 时给出清晰引导而非报错崩溃 |

## 四、关键技术决策点（开工前确认）

| # | 决策 | 推荐方案 | 理由 |
|---|------|---------|------|
| D1 | Tauri 前端：复用 web/ 还是新写？ | **复用 web/**，加 Transport 抽象 | 已有 20+ 组件、双语、向导流程，重写成本高 |
| D2 | soma-server 是否保留？ | **保留**，作为 headless 服务器模式 | 服务器/CI 场景仍需要 HTTP；Feature 层两宿主共用 |
| D3 | FFmpeg 策略 | M2 系统安装 + 探测引导；M3 评估 sidecar 捆绑 | 先保证可用，再优化开箱体验 |
| D4 | 数字人引擎在桌面版的默认值 | **Live2D**（纯 CPU），GPU 引擎（EchoMimicV3）标记为「高级/需 GPU」 | 桌面用户大概率无 N 卡；Live2D 零成本 |
| D5 | 私有 kit 依赖 | 维持路径依赖，构建机约定 `~/workspace/media/kit`；后续再考虑抽公共 crate 发布 | 0.1.2 不扩大改造范围 |
| D6 | 功能点输入输出格式 | JSON Schema 化（serde 定义即 Schema），为将来插件化/第三方调用铺路 | 与现有 serde 栈零成本 |

## 五、风险清单

| 风险 | 影响 | 缓解 |
|------|------|------|
| pipeline 改造引入回归 | 老任务流水线断掉 | M1.2 保留旧 API 兼容层；用现有 6 步任务做回归用例；`0.1.1` 分支可随时回退 |
| Tauri + Actix-Web 双宿主并发冲突 | 任务队列/SQLite 锁问题 | Feature 层统一走已有 TaskQueue 与 SQLite WAL；两宿主不混跑 |
| 前端 Transport 双轨维护成本 | 两套行为不一致 | Transport 接口保持极薄（只做参数转发），业务逻辑全在后端 |
| 外部依赖（FFmpeg/Python）在用户机器缺失 | 桌面开箱体验差 | M2.5 探测 + 引导；数字人默认 Live2D |
| Windows/Linux 无构建环境 | 无法产出三平台安装包 | M3.4 用 GitHub Actions（matrix 构建）；注意私有 kit 需 vendored 或私有仓 |
